## 2. 핵심 논쟁과 합의

### 논쟁 A — 심장질환 감지 제품인가, 안전 보조 제품인가

- 의료·데이터 역할은 현재 심박 센서 하나만으로 심정지·심근경색·부정맥을 주장할 수 없다고 판단했습니다.
- 사업 역할은 강한 마케팅 문구가 초기 관심 확보에 유리하다고 주장했습니다.
- 안전·정책 역할은 기능보다 강한 표현이 사용자 오해와 규제 위험을 키운다고 반박했습니다.

**결정:** 1차 제품은 `심박 및 낙상 후보 안전 보조 앱`으로 제한합니다. 의료 진단 표현은 검증과 규제 계획이 수립될 때까지 금지합니다.

### 논쟁 B — 자동 119 신고를 유지할 것인가

- 응급 UX 역할은 무반응 사용자를 위해 자동화가 필요하다고 주장했습니다.
- 안전·보안·QA 역할은 오탐, 고정 위치, SMS 성공 확인 부재, 사용자 취소 경로 부재 때문에 현재 자동 신고가 더 위험하다고 판단했습니다.

**결정:** 자동 SMS와 자동 통화를 제거합니다. 현재 버전은 사용자 확인 후 시스템 119 다이얼러를 여는 수준으로 제한합니다.

### 논쟁 C — 충격 4.5G 이후 10초 타이머만으로 충분한가

- 초기 구현은 단순성과 빠른 반응을 우선했습니다.
- IMU·신호·QA 역할은 충격 후 실제 움직임을 측정하지 않아 시계 낙하와 손목 충격을 쓰러짐으로 처리한다고 지적했습니다.

**결정:** 충격 이후 샘플 분산, 중력 크기 안정성, 최근 유효 심박을 함께 확인합니다. 임계값은 제품 기준이 아니라 시험용 기본값으로 표시합니다.

### 논쟁 D — Flutter 단일 앱인가, 네이티브 Wear 앱과 모바일 앱 분리인가

- Flutter 역할은 빠른 UI 개발과 코드 공유를 선호했습니다.
- Wear OS·성능 역할은 장시간 센서 수집, Health Services, 포그라운드 실행과 배터리 제어는 Kotlin이 더 적합하다고 판단했습니다.

**결정:** 현재 Flutter UI는 유지하되 장기 목표는 `Kotlin Wear OS 안전 엔진 + Flutter 보호자 모바일 앱`입니다.

### 논쟁 E — Neo4j·Graph RAG를 초기부터 사용할 것인가

- 데이터·AI 역할은 장기 기록 설명과 지식 검색에 활용 가능하다고 보았습니다.
- 안전·SRE 역할은 응급 경로에 네트워크와 비결정적 AI를 넣으면 장애와 설명 불가능성이 증가한다고 반박했습니다.

**결정:** 응급 판정은 로컬 결정론적 상태 머신으로 구현합니다. Neo4j와 LLM은 MVP에서 제거하고 추후 비응급 분석에만 검토합니다.

### 논쟁 F — Python SQLite 엔진을 앱에 유지할 것인가

- 데이터 역할은 현재 스키마가 개념 검증에 유용하다고 평가했습니다.
- 모바일 역할은 Python 파일이 Wear OS APK 런타임과 연결되지 않는다고 지적했습니다.

**결정:** Python 코드는 참고용 실험으로 격리하고, 실제 Wear 저장소는 Room으로 다시 구현합니다.

### 논쟁 G — 어떤 기능을 1차 성공으로 볼 것인가

**합의된 1차 성공 기준:**

1. 실제 Wear OS 기기에서 빌드·설치된다.
2. 사용자 권한을 올바르게 요청한다.
3. 실제 심박 값을 표시한다.
4. 정상 활동 중 불필요한 안전 알림이 발생하지 않는다.
5. 충격 후 움직임이 있으면 후보를 폐기한다.
6. 충격 후 저활동과 착용 신호가 함께 있으면 안전 확인을 표시한다.
7. 119 다이얼러는 열리지만 자동 통화·SMS는 실행하지 않는다.
8. 모든 위험 이벤트에 재현 가능한 시험 기록이 남는다.

## 3. 이번 반영 범위

- Flutter와 Android 네이티브 채널 연결
- 센서 런타임 권한 요청
- 자동 SMS와 위치 고정값 제거
- 장시간 WakeLock 제거
- 포그라운드 알림 문구를 실제 기능과 일치시킴
- 충격 이후 저활동 분산 검사 추가
- 최근 유효 심박을 보조 착용 신호로 사용
- 낙상 후보를 Flutter 안전 확인 화면으로 전달
- 15초 무응답 시 119 다이얼러만 실행
- README, 안전, 아키텍처, 로드맵, 시험 문서 추가

## 4. 보류된 쟁점

- Health Services 전환 전 원시 SensorManager 코드를 얼마나 유지할지
- 실기기별 임계값 보정 전략
- 워치 단독 LTE와 휴대전화 중 어느 장치가 응급 연락을 담당할지
- 보호자 알림 실패 재시도 방식
- 데이터 암호화 키의 기기 간 동기화
- 비의료 건강지원기기와 의료기기 중 최종 출시 경로

## 5. PM 최종 결정

첫 번째 릴리스 목표를 기능이 많은 데모가 아니라 **안전하게 실패하는 빌드 가능한 프로토타입**으로 정의합니다. 다음 개발은 문서에 적힌 단계 순서를 변경하지 않으며, 실기기 시험을 통과하지 않은 자동 신고 기능은 병합하지 않습니다.
